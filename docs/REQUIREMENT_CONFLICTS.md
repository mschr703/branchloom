# Requirement conflicts (F04 first slice)

The **Decisions → Conflicting requirements** section compares explicit card acceptance criteria. It does not infer meaning from titles or arbitrary prose.

1. Create concrete acceptance criteria on two cards. In **Decisions**, select each source criterion and mark its component, scope, property, and stance (**required** or **forbidden**). The original criterion text stays unchanged.
2. Branchloom shows a possible conflict only when two active rules belong to different cards, have the same normalized component, scope, and property, and have opposite stances. The UI displays both verbatim statements, card links, the presumed common scope, and why the pair was flagged.
3. Choose which source rule applies or dismiss the hint as different contexts. A reason is mandatory. The main process rechecks both criteria and card content revisions immediately before saving. If either changed, the decision is rejected until the sources are refreshed and reviewed again.
4. The decision is append-only evidence with both original statements and card revision numbers. It appears in the decision history and on both card panels after restart. A later card edit marks the old decision historical. Removing a classification does not delete an earlier decision or change either criterion.

### Hints for new acceptance criteria

In **Decisions → Conflicting requirements**, **Refresh hints** reads current acceptance criteria and existing explicit rule classifications in this project. An unclassified criterion is suggested only if its full sentence matches a current classified statement after removing exactly one opposing modal: English `must` versus `must not`, or German `muss` versus `darf nicht`. Other negation, multiple modal phrases, changed wording, differing width or context, and very short sentences are excluded. The component, scope, and property shown in the hint are copied from the existing classification; Branchloom has not derived them from the new text. Both original statements, card links and revisions, assumed scope, matching reason, and uncertainty are visible. The search checks at most 300 current criteria against the first 200 marked rules and shows at most 50 hints; truncation is indicated.

**Review rule marking** only fills the existing form. The user checks the assumed scope and clicks **Mark rule** to classify it. The main process checks the candidate criterion, card revision, existing source statement/revision, stance, and classification keys again. A changed source rejects the old hint. Only after this manual classification does the ordinary conflict decision appear, where the user chooses a rule or dismisses the hint with a reason. Original statements are never rewritten. Hints are transient; classifications and decisions persist as before. Card titles and descriptions are not automatically parsed, and paraphrased or semantically equivalent requirements are not detected. Add or update explicit acceptance criteria first; use **Refresh hints** if the Decisions view was already open.

This is a deterministic aid for deliberately classified rules. A shared key is not proof of a real contradiction; the user decides. Classification, refreshing, and resolving are manual. A changed card revision conservatively marks its rule stale even if the edit did not affect that criterion. The view checks at most 200 active rules and displays at most 100 conflicts and 500 decisions per project, with a visible limit notice. Semantic analysis, automatic classification of incoming card prose, and more complex conditions remain open.
