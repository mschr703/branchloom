# Local development accounts (F08 partial implementation)

In a card drawer, first start the card's managed **Karten-Vorschau**. Open **Dev-Konto**, register a project account with the app name, environment, role, subject and a local identity endpoint such as `/api/me`, then explicitly assign it to the card. A second card can be assigned a different account. The assignments survive app restarts; they are not included in project-package exports.

**Anmeldefenster öffnen** opens the ready card preview in a visible Electron window. Each account gets a separate, memory-only Chromium partition. The window can navigate and send requests only to that preview's exact local origin while its assigned card grant and managed preview run are still valid; each network request checks both again. Downloads, new windows and browser permissions are denied. Login happens in that window; Branchloom never asks for a password or stores a token in its SQLite records, card text, prompts or its own account logs. The target app controls its own server logs and may log request headers. An agent does not receive this session. A changed card grant or a restarted preview closes the old window.

After login, **Zugang prüfen** makes a credentialed GET through the same account partition to the configured path on the current card-preview origin. The target app must return HTTP 200 JSON with exact `subject` and `role` fields. HTTP 401 or a login redirect means login is missing or expired; HTTP 403 means access was denied; a different subject/role is reported as the wrong account. The response is bounded to 4 KiB and its body is neither stored nor forwarded to an agent. This is an observation from the target app, not an independent proof of its identity. Port changes keep the card assignment but require a fresh preview and login check. **Zuweisung entziehen** closes that card's window; **Anmeldung vergessen** clears the account's in-memory browser storage.

## Optional local test-account creation

A project can implement the following **local development endpoint** to let Branchloom create a test account after an explicit user click. In the card drawer, assign an existing provisioner account, start that card's managed preview, log into its visible account window, and save the relative seed path under **Testkonto in dieser App anlegen**. Create a second project account record for the desired role and subject in the same service and environment. Select it, click **Zielkonto prüfen**, inspect the result, then click **Jetzt anlegen** only if the target is missing. This is a separate action from registering Branchloom's account metadata.

The preview's identity endpoint must first return exact `subject` and `role` for the provisioner. The seed endpoint must then accept a credentialed `GET <path>?subject=<encoded subject>&role=<encoded role>` and return HTTP 200 JSON `{ "subject": "...", "role": "...", "exists": false }` (or `true`). For a missing account, Branchloom issues a credentialed `POST <path>` only after the second click, with JSON `{ "subject": "...", "role": "...", "requestId": "..." }`. The target app must authorize the provisioner itself, enforce the requested role, and make creation idempotent by subject and request ID. It must return HTTP 200 or 201 JSON `{ "subject": "...", "role": "...", "exists": true, "requestId": "...", "created": true }` (`created: false` if another actor already created it). Branchloom checks exact values, refuses redirects and responses over 4 KiB, and uses only the currently assigned account's isolated browser session against the currently managed loopback preview. It rechecks the account and target immediately before POST. The one-time missing-account check expires after five minutes and is invalid after a grant, run or path change.

The local database stores the endpoint path and minimal attempt status, not cookies, request headers, response bodies or passwords. An interrupted POST has **unknown** outcome after restart and is never replayed automatically; run a new GET to see whether the target exists. If the target application's own database is reset, a new GET can detect that the account is missing again. The app's own server logs may contain the request subject and role. There is no automatic password generation, email verification bypass, arbitrary service provisioning, or agent access to these sessions.

The partition deliberately does **not** persist cookies after Branchloom exits. The user must sign in again after restart, while project accounts, card grants and seed endpoint config remain. Protected persistent login and broader F08 acceptance remain open. The current F01 preview must be ready and managed by this app instance; an orphaned process is not trusted as an account target.
