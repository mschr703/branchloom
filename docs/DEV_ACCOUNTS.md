# Local development accounts (F08 partial implementation)

In a card drawer, first start the card's managed **Karten-Vorschau**. Open **Dev-Konto**, register a project account with the app name, environment, role, subject and a local identity endpoint such as `/api/me`, then explicitly assign it to the card. A second card can be assigned a different account. The assignments survive app restarts; they are not included in project-package exports.

**Anmeldefenster öffnen** opens the ready card preview in a visible Electron window. Each account gets a separate, memory-only Chromium partition. The window can navigate and send requests only to that preview's exact local origin while its assigned card grant and managed preview run are still valid; each network request checks both again. Downloads, new windows and browser permissions are denied. Login happens in that window; Branchloom never asks for a password or stores a token in its card text, prompts or normal logs. The target app controls its own server logs and may log request headers. An agent does not receive this session. A changed card grant or a restarted preview closes the old window.

After login, **Zugang prüfen** makes a credentialed GET through the same account partition to the configured path on the current card-preview origin. The target app must return HTTP 200 JSON with exact `subject` and `role` fields. HTTP 401 or a login redirect means login is missing or expired; HTTP 403 means access was denied; a different subject/role is reported as the wrong account. The response is bounded to 4 KiB and its body is neither stored nor forwarded to an agent. This is an observation from the target app, not an independent proof of its identity. Port changes keep the card assignment but require a fresh preview and login check. **Zuweisung entziehen** closes that card's window; **Anmeldung vergessen** clears the current and saved login for that one account.

On Windows, the account window, identity check, seed endpoint and protected login reuse also require the F01 preview listener to belong to the managed server process or one of its children. Account-partition network requests check that owner again before release; concurrent requests share an in-flight asynchronous check so a child-server lookup does not block Electron's main thread once per asset. An unknown or foreign listener is denied, including when another process takes over a previously ready port. Branchloom never stops that foreign process. On other operating systems, the current F01 listener check remains the documented HTTP-marker fallback; it does not prove process ownership. A process can still change between a successful check and an actual network send, so the check is not a cryptographic binding.

## Explicit protected login reuse on Windows

After **Zugang prüfen** confirms the exact assigned identity, **Anmeldung für Neustart speichern** captures up to 32 cookies for the preview's exact local host from that account's memory-only session. It encrypts the bounded snapshot with Electron's asynchronous `safeStorage` backed by Windows DPAPI and stores only the encrypted blob and save time in Branchloom's local app-profile SQLite database. This opt-in does not persist the full Chromium partition, browser cache, Local Storage, IndexedDB, passwords, or an agent capability. The saved snapshot is tied to the account ID and local host, not the port. On a later Branchloom process start, a card with the same account grant and a ready managed preview can load those cookies into its own new memory-only partition; the identity check still has to succeed against the target app. A new port for the same host is supported. A different host, expired cookies, unavailable OS encryption, or a revoked grant prevents restoration. The panel distinguishes unsaved, saved, restored and unavailable states.

The saved blob is protected against other Windows users by the current user's DPAPI context, **not** against another program running as the same Windows user. Branchloom itself and the target app can access the login while it is active. The target app can revoke or expire the session at any time. If it relies only on Local Storage/IndexedDB or a cookie for another host, this cookie-only reuse will not restore that login. To refresh an expiring cookie snapshot, verify the account and click **Anmeldung für Neustart speichern** again. **Anmeldung vergessen** deletes the encrypted snapshot and clears the current account's browser storage; it does not affect another account. Removing a card assignment immediately denies that card access, while a saved login for the same account can still be used by another explicitly assigned card. On systems without verified Windows DPAPI support, the save action reports that protected storage is unavailable and manual login remains possible. These choices follow [Electron's session](https://www.electronjs.org/docs/latest/api/session), [Cookies](https://www.electronjs.org/docs/latest/api/cookies) and [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) APIs.

## Optional local test-account creation

A project can implement the following **local development endpoint** to let Branchloom create a test account after an explicit user click. In the card drawer, assign an existing provisioner account, start that card's managed preview, log into its visible account window, and save the relative seed path under **Testkonto in dieser App anlegen**. Create a second project account record for the desired role and subject in the same service and environment. Select it, click **Zielkonto prüfen**, inspect the result, then click **Jetzt anlegen** only if the target is missing. This is a separate action from registering Branchloom's account metadata.

The preview's identity endpoint must first return exact `subject` and `role` for the provisioner. The seed endpoint must then accept a credentialed `GET <path>?subject=<encoded subject>&role=<encoded role>` and return HTTP 200 JSON `{ "subject": "...", "role": "...", "exists": false }` (or `true`). For a missing account, Branchloom issues a credentialed `POST <path>` only after the second click, with JSON `{ "subject": "...", "role": "...", "requestId": "..." }`. The target app must authorize the provisioner itself, enforce the requested role, and make creation idempotent by subject and request ID. It must return HTTP 200 or 201 JSON `{ "subject": "...", "role": "...", "exists": true, "requestId": "...", "created": true }` (`created: false` if another actor already created it). Branchloom checks exact values, refuses redirects and responses over 4 KiB, and uses only the currently assigned account's isolated browser session against the currently managed loopback preview. It rechecks the account and target immediately before POST. The one-time missing-account check expires after five minutes and is invalid after a grant, run or path change.

The local database stores the endpoint path and minimal attempt status, not cookies, request headers, response bodies or passwords. An interrupted POST has **unknown** outcome after restart and is never replayed automatically; run a new GET to see whether the target exists. If the target application's own database is reset, a new GET can detect that the account is missing again. The app's own server logs may contain the request subject and role. There is no automatic password generation, email verification bypass, arbitrary service provisioning, or agent access to these sessions.

Without the explicit save action, the partition does **not** persist cookies after Branchloom exits. Project accounts, card grants and seed endpoint config remain. The current F01 preview must be ready and managed by this app instance; an orphaned process is not trusted as an account target. Broader external service logins and automatic credential refresh remain outside this local F08 implementation.
