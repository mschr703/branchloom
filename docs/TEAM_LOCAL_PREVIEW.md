# Local team preview

This preview runs one authenticated coordinator on the owner's laptop. It binds only to `127.0.0.1`, so a second app instance on the same laptop can join; colleagues on other devices cannot connect yet. The hosted project stays in the owner's local SQLite database. Joining does not copy the project repository, source files, CLI credentials, or browser profile.

## Start two separate local clients

Use Windows, Node.js 24, Git, and a clean source checkout. Run `npm ci`, `npm run build`, and `npm run typecheck` once in the Branchloom folder. Then open two PowerShell windows in that folder:

```powershell
# Window 1: owner profile
$env:BRANCHLOOM_DEV_USER_DATA = Join-Path $env:TEMP 'branchloom-team-owner-preview'
npm start
```

```powershell
# Window 2: member profile
$env:BRANCHLOOM_DEV_USER_DATA = Join-Path $env:TEMP 'branchloom-team-member-preview'
npm start
```

The profile paths must be distinct absolute paths. They retain the preview's local data and encrypted credentials across restarts. Do not use a profile that contains your regular Branchloom projects unless you intend to keep this preview there.

1. In the owner window, add an existing local Git project and open **Team**. Create a workspace with your display name. The coordinator starts locally and reuses its saved port after an app restart.
2. Choose a role and create an invitation. Copy its coordinator address and secret to the member window. The secret is shown once. It expires and cannot be used by a different member after acceptance.
3. In the member window, open **Team**, enter the address, invitation secret, and display name, and join. If the acceptance response is lost, use the visible retry option; the client reuses the same protected credential and request ID. Both profiles can inspect members with access to the selected project; the owner's list also shows members with no access. In the owner window, choose **Refresh members** after the colleague joins. The owner can use **Change role** with a second confirmation click. Changing a role clears that member's extra project capability grants, so review their rights afterwards. Expand **Project rights** to narrow access to read-only or none, or explicitly grant **Task controls** or **Agent start**. Each grant needs a second click and only works with full project access. Admins already have both through their team role.
   To add another local project, select it in the owner window, open **Team**, choose the existing workspace, and confirm **Add project**. Current and future members cannot see that project until you explicitly set their project access to read or edit. The initial workspace project keeps its role-based access.
4. In the member window, choose **Gemeinsames Board öffnen** from Team. This board reads the host's current cards; it does not create a local project copy. Select the same card in both windows and edit its shared draft. An authenticated event stream shows members currently viewing this card and notifies the other editor immediately; a five-second poll remains as a fallback. The editor distinguishes live connection from saved draft state. If delivery is uncertain, use **Retry** to resend the same pending mutation rather than creating another change. The accepted card description does not change. A viewer can read the draft but cannot edit it unless the owner explicitly grants the project capability.
5. Close and reopen the app. The coordinator restarts on the saved local port. Pending encrypted draft updates are replayed when that card's editor opens again. An open owner editor also reconnects after a short coordinator restart. A visible Electron test edits the draft while the coordinator is stopped, keeps the encrypted update pending for a polling interval, and verifies one replay after restart. A disconnected client may show an error until the host is running. Lost-response replay is also covered; long network outages and two physical machines are not yet verified.

Members with `manage_task` rights may change a card's priority or move it between columns through separate revisioned controls. Moving into an auto-start column additionally requires `start_agent`. The control warns that the configured CLI runs on the owner's laptop in a separate Git worktree. The coordinator records the move and one launch intent under the same mutation ID; a lost-response retry reports the original result without starting another session. If the worker cannot start, the move remains committed and the launch failure is shown. A crash between dispatch and recording its session ID leaves an uncertain `dispatching` result; it is not automatically replayed. This preview does not yet offer a persistent repair screen for that state. If the card changed before the first command arrives, Branchloom shows a conflict and asks for an explicit reload. A move is blocked while the project queue, the card's agent session, or an active workflow involving that card is running. Shared text edits cannot change board metadata. Open card views receive an authenticated event for a priority or column change and reload the board; the three-second board poll remains a fallback.

The owner can revoke a member in the Team setup. The next authenticated request is rejected and the member's open shared Board clears its cached cards. The current UI changes project access, member role, `manage_task`, and `start_agent`; other grants do not yet have UI. A shared draft cannot yet be accepted as the authoritative card or approved by a project admin; that is a separate upcoming command. Newly added projects still reside on the same laptop; adding one does not synchronize its source checkout. A source smoke runs two separate Electron processes with independent profiles and checks live presence, edits, and recovery after an orderly owner restart: `npm run smoke:team-two-process`. After that build, `node scripts/smoke-team-two-process.mjs --crash-owner` also checks recovery after an abrupt owner-process termination, including one automatic replay of the offline draft. Windows team credentials use a DPAPI-protected key stored before the encrypted team files; PowerShell must be available. These smokes do not prove recovery from every power loss or long outage. For a second laptop on the same tailnet, see the [Tailscale preview](TEAM_TAILNET_PREVIEW.md). The [team design](TEAM_SYNC.md) describes the wider roadmap.
