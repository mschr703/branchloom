# Product feedback · 27 November 2026

This is the user's review of the current Branchloom preview and seven visual references. It is a work list, not a claim that the proposed features already work. The screenshots were shared in chat and are not copied into the public repository. `docs/STATUS.md` records verified implementation. Release `v0.1.3` is the baseline for this follow-up; items below need their own verification before being marked complete.

## Product direction

Keep one authoritative project board and let planning, agents, and teammates act on that same work. The interface should be calm enough to scan quickly, with direct manipulation and clear ownership when work is active. Use the references for density, hierarchy, and interaction quality without copying their layout or displaying fabricated people, progress, or notifications.

The wider team planning flow remains a joint product discussion: how a team starts from an unstructured idea, communicates in context, drafts a plan, and adopts it into the shared board. The user asked to discuss this before treating a particular interaction as settled.

The user emphasized F26 twice: a small color change to column backgrounds alone is not sufficient; individual task cards and the board composition need the same design review. The user also reiterated the intended paid VPS team mode. Its current design boundary is in [TEAM_HOSTING.md](TEAM_HOSTING.md); the service and entitlement enforcement are not shipped.

## Delivery order

1. First verify the `v0.1.3` release and give testers its installer link. Keep new changes on `main` after the release tag.
2. Fix immediate clarity and layout gaps: F04, F10, F03's New workflow entry, F09's Ideas-first path, then F19 and F18/F16 with screenshot checks.
3. Build factual activity signals and a usable Team dashboard: F01, F21, F05, F06. Confirm local presence before representing remote teammates.
4. Deepen planning and product context: F03's agent proposal, F11–F15, F17, F20, F02, F23–F25. Split large items into vertical cards with acceptance tests.
5. Develop remote team work F07 through the coordinator/worker milestones in `TEAM_SYNC.md`. Design F22 with the user when requested.

Each finished slice needs a real user path, relevant API/UI tests, a source-backed status update, and a public-data scan before push. A visual signal must never imply a team member, agent result, or workflow step that the app has not observed.
